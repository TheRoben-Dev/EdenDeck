## Key findings

1. **Only `-f`, `-g <path>`, `-u <n>` work the same on Stable and Nightly.** Stable Qt has
   no `--config`; Nightly's `-i/--input-profile` and `-d/--debug` are broken in Eden's
   own parser, and the Stable spelling `-input-profile` would hit that bug on Nightly.
2. **Enums are stored as integer indices** and the tables differ between versions
   (`gpu_accuracy`: Stable 0/1/2 = Low/Medium/High, Nightly 0/1 = Low/High). Copying
   values between versions silently changes settings. The adapter translates by name.
3. **Two settings moved INI sections** (`fast_cpu_time`, `fast_gpu_time` → `[System]`) and the
   shader cache moved from the data dir to `~/.cache/eden/shader` on Nightly.
4. **Disabled add-ons** are a global `[DisabledAddOns]` array keyed by decimal title ID and
   exact add-on names, so mods can be toggled without moving files. Mod load order is
   alphabetical by folder name, and the first folder wins.
5. **Eden rewrites every INI it loads and drops unknown keys.** EdenDeck must keep its own
   data separately and write Eden files only while Eden is closed.
6. **Eden already has spatial FSR 1** (`scaling_filter=Fsr`) on both channels, and **Nightly
   has built-in Lossless-Scaling frame generation** (needs the user's own `Lossless.dll`, with a
   target-rate setting). That changes how phase 5 should be built (see "Direction question").
7. **Eden's own updater has no Linux AppImage path**, so the Eden manager handles Linux
   updates using the official `stable./nightly.eden-emu.dev/latest/release.json` feeds.

## Assumptions

* The GitHub mirror `eden-emulator/mirror` matches git.eden-emu.dev (not cross-checked:
  that host is blocked from the build environment).
* v0.2.1 is the current Stable (newest tag on the mirror as of 2026-11-22).
* The official Eden AppImage launches the Qt `eden` binary and uses the system Vulkan loader,
  or a bundled one recent enough for `VK_ADD_LAYER_PATH` (loader 1.3.234+).
* Godot 4.5+ joypad input (SDL3-backed) exposes enough device info (vendor/product, name) to
  tell Steam Virtual Gamepads from physical pads and pick glyphs. Otherwise we P/Invoke SDL3
  directly.
* Users bring their own keys, firmware, games and, for frame gen, their own Lossless Scaling copy.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| AppImage bundles an old Vulkan loader that ignores `VK_ADD_LAYER_PATH` | layer not loaded | implicit manifest gated by `ENABLE_EDENDECK_LAYER=1` (built and tested) |
| Qt `eden` window stays open after the game exits, or exclusive fullscreen misbehaves under gamescope | clunky return to EdenDeck | frontend owns the process lifetime; set `fullscreen_mode` per launch; evaluate `eden-cli` (needs a merged config since it ignores per-game files) |
| Eden changes keys/enums again (it changed several in 6 months) | wrong settings written | versioned schema snapshots, translate by name, CI job regenerates snapshots from Nightly and fails on drift |
| Flatpak sandbox vs. Eden AppImage (no FUSE, GPU/driver/layer alignment) | Flatpak build can't launch Eden cleanly | run Eden on the host via `flatpak-spawn --host`; self-hosted remote, not Flathub; AppImage build unaffected |
| A present-time FSR 3 layer has no motion vectors, depth or HUD-less colour | poor temporal upscaling / frame-gen quality | spec already calls this out; see direction question below |
| Lossless.dll location differs per Steam setup | frame gen unavailable | scan `libraryfolders.vdf` (native + Flatpak Steam), and offer a manual file pick |

## Verification steps

**Done in the build environment (software Vulkan, X11 via Xvfb, no Eden):**

* Layer builds cleanly with `-Wall -Wextra`, links no `libvulkan`, and exports only the three
  loader entry points.
* `vkcube` through the layer: instance/device/swapchain hooked, 300/300 presents counted,
  stats JSON written, usage patch accepted.
* Kill switch, and implicit manifest enable/disable env, all behave as designed.
* Khronos validation, placed above and below our layer: zero validation messages.
* `frame_stats_test` passes.

**Needs real hardware (procedure in `layer/README.md`, Eden checklist in
`docs/eden-integration.md` §10):** layer inside Eden on desktop X11, Wayland, nested
gamescope and Steam Deck/Ally Game Mode, on Stable and Nightly; AppImage contents; release
asset names and digests; per-game config and DisabledAddOns behaviour on a live install.

## Phase 5 direction (decided 2026-11-22: option A, "Eden built-ins, layer = overlay")

Given finding 6, phase 5 changes phase 5 from "build FSR 3 upscaling + frame gen in our
layer" to:

* **Upscaling:** offer "Eden internal resolution" + "FSR (Eden built-in)" + "SGSR (Nightly)",
  all driven through Eden's own settings. Drop our layer's spatial FSR, which would run on a
  frame Eden has already scaled.
* **Frame gen (capped at 60, 2x only):** use Eden Nightly's built-in Lossless frame gen with
  the user's own Steam copy of Lossless Scaling (`frame_gen_target_rate=60`,
  `frame_gen_multiplier=2`). Use standalone lsfg-vk for Stable. Keep an FSR 3.1 frame-gen
  path in our layer only as an experimental option for users without Lossless Scaling.
* **Our layer's main job becomes the in-game overlay and quick menu** (FPS / real vs.
  generated, frame-time graph, hotkey menu), which Eden has no equivalent for.
